# Modelo de datos: cuentas, sesiones y pertenencia

**Estado**: Diseño para implementación. PostgreSQL 17, UTF-8, locale `C.UTF-8`
igual en todos los ambientes. Instantes en UTC con `timestamptz`; importes decimales
se intercambian como cadenas. Identificadores de código en inglés.

## User → users

| Campo | Tipo y regla |
|---|---|
| `id` | `bigint GENERATED BY DEFAULT AS IDENTITY`, PK; se expone como cadena |
| `name` | `varchar(100) NOT NULL`; 1–100 caracteres tras recorte exterior |
| `email` | `varchar(254) NOT NULL`; correo validado y sin whitespace exterior |
| `email_normalized` | `text GENERATED ALWAYS AS (...) STORED`; expresión canónica |
| `password_hash` | `varchar(255) NOT NULL`; Argon2id, nunca una contraseña en claro |
| `created_at` | `timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP` |
| `updated_at` | `timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP`; aplicación actualiza al modificar |

Expresión de `email_normalized`:

```sql
lower(btrim(email, chr(32) || chr(9) || chr(10) || chr(13) || chr(12) || chr(11)))
```

`UNIQUE(email_normalized)` nombrado `users_email_normalized_unique`. El índice
subyacente garantiza unicidad concurrente por correo equivalente. Login y limitador
usan el mismo resultado calculado en PostgreSQL a partir de la entrada; no replican
el algoritmo en PHP. No se colapsan alias o puntos. Rechazar NUL, whitespace interno
y formato inválido antes de insertar. Aplicar límites a la entrada para no procesar
cuerpos ilimitados. La base también verifica nombre no vacío y correo no vacío.
La confirmación de contraseña es transitoria y no tiene columna.

## ServerSession → server_sessions

| Campo | Tipo y regla |
|---|---|
| `token_hash` | `char(64)` PK; SHA-256 del identificador aleatorio de 256 bits |
| `user_id` | `bigint NULL REFERENCES users(id) ON DELETE RESTRICT`; nulo antes de autenticar |
| `payload` | `jsonb NOT NULL`; datos del contenedor Mezzio y estado CSRF, sin finanzas ni contraseña |
| `created_at` | `timestamptz NOT NULL` |
| `authenticated_at` | `timestamptz NULL`; inicio del límite absoluto autenticado |
| `last_activity_at` | `timestamptz NOT NULL` |
| `expires_at` | `timestamptz NOT NULL`; máximo 7 días desde autenticar; 15 minutos para sesión anónima |
| `revoked_at` | `timestamptz NULL` |

Estados: anónima → autenticada con nuevo identificador; autenticada → revocada por
logout o regeneración; cualquier sesión → vencida por tiempo. Una sesión revocada o
vencida nunca regresa a autenticada. Se admite varias sesiones independientes por usuario.

La vigencia autenticada requiere `revoked_at IS NULL`, edad desde
`authenticated_at < 7 días` e inactividad `< 24 horas`. Igualdad con el límite ya es
vencimiento. Las verificaciones pasivas de `/api/auth/session` no actualizan actividad.
Las consultas o acciones iniciadas por el usuario sí lo hacen; el frontend no hace
polling de rutas financieras ni envía actividad por temporizador.

`PostgresSessionPersistence` bloquea la fila con `SELECT ... FOR UPDATE` en una
transacción que envuelve la petición API y la persistencia de la sesión. Usa la misma
conexión/unidad de trabajo que las operaciones de negocio; no se abren transacciones
anidadas. Las violaciones SQL esperadas se aíslan mediante savepoints y se hace
`ROLLBACK TO SAVEPOINT` antes de convertirlas en errores funcionales; no se confirma
una transacción abortada. La respuesta se emite solo después del commit. Ante excepción se revierte;
un error funcional esperado se representa como respuesta y puede confirmar el conteo
de fallos. Ante logout/regeneración se revoca la fila anterior y solo se inserta un
identificador recién generado por el servidor. Una petición concurrente con token
anterior, al obtener el bloqueo, vuelve a comprobar revocación y tiempo. No se usa un
upsert capaz de recrear sesiones revocadas. Los bloqueos se toman siempre en orden:
sesión, limitador, usuario, recursos; probar ausencia de resurrección y carreras.

Limpieza programada elimina sesiones caducadas/revocadas cuando ya no son utilizables;
no determina la autorización ni prolonga plazos. Cookie y validación de servidor tienen
límites independientes; que exista cookie no acredita vigencia.

## LoginThrottle → login_throttles

| Campo | Tipo y regla |
|---|---|
| `key_hash` | `char(64)` PK; HMAC de correo normalizado + IP efectiva con secreto del servidor |
| `failed_at` | `timestamptz[] NOT NULL`; últimas marcas dentro de ventana de 15 minutos |
| `blocked_until` | `timestamptz NULL` |
| `updated_at` | `timestamptz NOT NULL` |

La IP efectiva se obtiene solo de cadena de proxies confiables; no de `Origin` ni de
un `X-Forwarded-For` arbitrario. Dos dispositivos bajo la misma NAT pueden compartirla.
El secreto no se entrega al cliente; los contadores tampoco distinguen cuentas existentes.

Crear fila si falta y bloquearla transaccionalmente, purgar marcas de más de 15 minutos,
verificar credenciales y registrar fallo. La ventana conserva solo marcas
`failedAt > now - 15 minutos`; una marca exactamente en el límite inferior ya caducó. El quinto fallo fija `blocked_until=now+15min`.
Los cuatro primeros fallos devuelven error genérico; el quinto y los intentos dentro de
la pausa devuelven el error temporal. Durante la pausa no se comprueba la contraseña ni
se amplía el plazo. Al cumplirse `blocked_until` se limpia el estado; un login exitoso
previo al límite también lo limpia. Mismo correo con otro uso de mayúsculas comparte
clave. Serializar la decisión completa evita superar el límite con solicitudes concurrentes.

## Pertenencia de clientes, proyectos y cobros

Contrato de las futuras tablas de dominio; se implementa con sus respectivas migraciones,
sin limitarse a añadir `user_id` en las pantallas:

| Tabla | Claves y restricciones obligatorias |
|---|---|
| `clients` | PK `id`; `user_id NOT NULL REFERENCES users(id)`; `UNIQUE(user_id,id)` |
| `projects` | PK `id`; `user_id NOT NULL REFERENCES users(id)`; `UNIQUE(user_id,id)`; FK `(user_id,client_id)` a `clients(user_id,id)` |
| `payments` | PK `id`; `user_id NOT NULL REFERENCES users(id)`; FK `(user_id,project_id)` a `projects(user_id,id)` |

FK de pertenencia con `ON DELETE RESTRICT`; nunca cascada implícita de registros
financieros. En la sección mínima, `projects.client_id` y `payments.project_id` son `NOT NULL`;
una FK compuesta con parte nula no garantiza esa relación y no se acepta como atajo.
Toda consulta, actualización y agregado añade `user_id` de sesión; la autorización
no acepta un titular enviado por el navegador. Actualizar por `(user_id,id)` y verificar
filas afectadas; cero filas produce el mismo 404 que un identificador inexistente.

Para acreditar el criterio técnico en esta implementación se necesita una sección
vertical mínima real, no mocks: migraciones `CreateClients`, `CreateProjects` y
`CreatePayments` con los campos básicos usados por los endpoints de aceptación.
No se implementa el CRUD completo ni los cálculos futuros de esos módulos. Esta base
incluye `clients.name`, `projects.name`, `projects.client_id`, `payments.project_id`,
`payments.client_paid_amount numeric(20,6)`, `payments.currency char(3)` y
`payments.paid_on date`, además de claves y fechas. `client_paid_amount > 0` y moneda
MXN en el recorrido de aceptación inicial; otros cálculos y monedas requieren su
especificación. El recorrido MXN acepta como máximo dos decimales y rechaza mayor precisión,
sin redondeo silencioso. El reporte suma exclusivamente el importe abonado por el
cliente, sin presentarlo como neto recibido. Los cobros de ejemplo no tienen deducciones.

`clients.name` y `projects.name` admiten de 1 a 100 caracteres después de quitar
espacios exteriores. La aplicación valida y persiste el valor recortado; las
migraciones limitan la longitud y rechazan nombres vacíos o con espacios exteriores.

`payments.idempotency_key` es obligatorio, con `UNIQUE(user_id,idempotency_key)`;
repetir la misma solicitud devuelve el cobro existente y un contenido diferente bajo
la misma clave devuelve conflicto. El detalle y reporte reutilizan la misma política de
pertenencia; cuando se incorpore saldo pendiente, ambos deben usar la misma regla.
Los campos adicionales de monto acordado, comisiones (`platformFee`), impuestos,
dinero recibido y conversiones llegarán con las reglas de cada módulo en migraciones
nuevas, sin reutilizar `client_paid_amount` para conceptos diferentes.

Los fixtures de Ana y Luis se crean por servicios de aplicación sobre estas tablas
migradas, no por una segunda estructura de pruebas. Reporte y actualización pasan por
los handlers y repositorios reales, con sesiones y CSRF reales. El total mensual usa
`paid_on >= monthStart AND paid_on < nextMonthStart`, suma decimal y devuelve cadena.

## Secuencia versionada de migraciones

1. `CreateUsers`: primera migración; tabla `users`, columna generada e índice único.
2. `CreateAuthenticationState`: `server_sessions` y `login_throttles`, sus índices y FK.
3. `CreateClients`: mínimo descrito y restricciones de titular.
4. `CreateProjects`: relación compuesta con cliente.
5. `CreatePayments`: relación compuesta, importe decimal e idempotencia.

Phinx agrega su historial `phinxlog`. Los timestamps únicos del nombre de archivo se
asignan al crear cada migración. No se edita una migración ya aplicada. `up()`/`down()`
explícitos cuando intervenga SQL de columnas generadas, checks o índices; no suponer
que `change()` invierte SQL arbitrario.

## Reversión y datos existentes

Las migraciones iniciales se prueban en una base desechable vacía. Un `down()` que
elimine una tabla solo se permite si está vacía, o si un procedimiento explícito ya
respalda y verifica sus datos; de otro modo aborta con explicación. No se ofrece un
rollback con pérdida silenciosa de cuentas o cobros. Reversibilidad del esquema no
implica reversibilidad de los registros.

Para una futura eliminación con datos: conservar columna/tabla anterior durante una
migración de expansión, copiar datos, validar conteos y valores, respaldar mediante
`pg_dump` y ensayar restauración en otra base. Eliminar en migración separada tras
verificar el cambio. Documentar restauración o declarar irreversible y recuperar
mediante respaldo. Recrear la tabla vacía nunca se presenta como recuperación.
